# RLM Sandbox — Architecture

How the hierarchical coding agent is organised, and why each piece is shaped
the way it is.

## Goals

1. **Code is generated by decomposition, not by one big prompt.** A task
   becomes a call-tree of small functions that each do one thing. Every
   generation step is scoped to a tiny, well-defined contract.
2. **The LLM is the minimum surface area.** It makes genuinely agentic
   decisions — what to design, what to decompose, what to test, what to
   put in a body. Everything else — test execution, dispatch order,
   project wiring, persistence, retries, finalization — is
   deterministic harness code.
3. **Tests are the contract at every level.** A function is not "done"
   until its tests are green. A branch assembly is not "done" until its
   integration tests are green against its real children. The project
   is not "done" until vitest + tsc pass.

## Core data structure: the DesignGraph

The graph is the single source of truth for the build. Files on disk
are an ephemeral serialisation so vitest can run.

### FunctionNode

```ts
type FunctionNode = {
  module: string
  name: string                 // globally unique (TS identifier, not "project")
  signature: Signature
  description: string          // planner-written
  tests: TestSpec[]            // UNIT tests — run in isolation, siblings stubbable
  integrationTests: TestSpec[] // ASSEMBLY tests — run with real children, no stubs
  implementation: string | null
  status: "declared" | "implementing" | "implemented" | "tests-green" | "tests-red"
  origin: "plan" | "load" | "manual"
  parent: string | null        // tree position
  children: string[]           // tree position
}
```

### Graph-level

```ts
type DesignGraph = {
  // …per-node mutations…
  addFunctionChild(parent, module, name, signature, description, origin)
  projectTests: TestSpec[]     // app-level integration tests
  topoSortFunctions(): FunctionNode[]  // depth-first, children-before-parent
  materialize(override?): Record<path, source>
}
```

### The test hierarchy

Three test tiers with different scopes and wiring:

| Tier | Where attached | Wiring | Ran when |
| --- | --- | --- | --- |
| **Unit** (`tests[]`) | Every function | `let ctx` — stubbing allowed | Dispatch of that function |
| **Integration** (`integrationTests[]`) | Branches only (fn.children.length > 0) | `const ctx` — no stubbing | Dispatch of the branch (after children green) |
| **Project** (`graph.projectTests[]`) | Graph scope | `const ctx` — all fns wired | Finalize |

The `--testNamePattern ^<name>\b` filter in vitest naturally picks up both
`describe("foo")` (unit) and `describe("foo (integration)")` (integration)
for a function's dispatch, while excluding `describe("project integration")`.
Finalize runs with no filter, so project tests run there.

## The pipeline

```
┌──────────────────────────────────────────────────────────────────┐
│                      design_plan(task)                           │
├──────────────────────────────────────────────────────────────────┤
│  phase 1  LLM lists top-level functions (name, sig, one-liner)   │
│  phase 2  per-fn: LLM writes rich description + UNIT tests        │
│  phase 2b LLM writes PROJECT integration tests                    │
│                                                                   │
│  [When invoked recursively with `parent: fnName`:]               │
│  phase 1  LLM lists CHILDREN of that parent                      │
│  phase 2  per-child: LLM writes description + UNIT tests         │
│  phase 2b LLM writes BRANCH integration tests for parent         │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│                         design_build                             │
├──────────────────────────────────────────────────────────────────┤
│  work-queue walk: findReady() picks next fn where                │
│     - status ≠ tests-green                                       │
│     - all children already tests-green                           │
│  dispatch(fn):                                                   │
│     1. askDecompose: IMPLEMENT or DECOMPOSE?                     │
│        - IMPLEMENT: go to step 2                                 │
│        - DECOMPOSE: call decompose() callback →                  │
│             runs design_plan(graph, …, { parent: fn.name })      │
│             children added, parent requeued                      │
│     2. body-generation loop:                                     │
│        prompt Implementer → extract fenced body → test_run →     │
│           green? save + return                                   │
│           red?   next attempt with failure digest (≤5 attempts)  │
│  on all functions green: finalize                                │
└────────────────────────────┬─────────────────────────────────────┘
                             ▼
┌──────────────────────────────────────────────────────────────────┐
│                         design_finalize                          │
├──────────────────────────────────────────────────────────────────┤
│  write all files to disk                                         │
│  vitest run  — runs every *.test.ts + *.integration.test.ts      │
│                + project.integration.test.ts                     │
│  tsc --noEmit                                                    │
│  if integration failures → reopen affected functions             │
│     (status tests-red, clear implementation) so next build       │
│     re-dispatches them with the failure context                  │
└──────────────────────────────────────────────────────────────────┘
```

## LLM vs. harness — the contract

The LLM is asked to do exactly these things, each in its own scoped call:

1. **Name the top-level functions** (phase 1, top-level plan).
2. **Write a function's description and unit tests** (phase 2, per-fn).
3. **Write project integration tests** (phase 2b, top-level plan).
4. **Decide IMPLEMENT or DECOMPOSE** for a function (askDecompose, one word).
5. **Name this function's children** (phase 1, recursive plan).
6. **Write branch integration tests** for an assembly (phase 2b, recursive).
7. **Write a function body** (dispatch body generation).

That's seven distinct prompts, each tightly constrained with an explicit
return shape (JSON with a schema, or a fenced code block).

Everything else — topo ordering, file emission, ctx.fns wiring, test
invocation, retry with feedback, graph mutations, finalize — is
deterministic code. Bugs live in the harness where we can fix them;
LLM output variance can't compound because each call has a narrow
contract and a parseable response.

## Why recursion matters

The graph is a **tree**, not a flat list, because:

1. A branch's assembly body only makes sense in the context of its
   children. The children go green first, the branch is dispatched
   with the child signatures spliced into its prompt, and the branch's
   body composes them.
2. Integration tests attach at each branch. A branch's integration
   tests exercise *its own* assembly — not the whole app. Failures
   localise.
3. Decomposition depth is adaptive. A "too complex to implement" branch
   becomes an Architect for its own subtree. The same pipeline runs
   again, one level deeper. `MAX_DECOMPOSE_DEPTH = 4` guards against
   runaway splitting.
4. Resume is natural. Interrupting mid-build leaves a partial tree in
   memory; the next call skips phase 1 (the graph already has
   plan-origin functions), skips phase 2 where tests are attached,
   skips dispatch where status is tests-green. Only the uncompleted
   work rerun.

## Why proc-ts

Adopted from [niquola/proc-ts](https://github.com/niquola/proc-ts) because
the constraints it imposes simplify the harness:

- **Filename = function name.** `materialize(override)` knows exactly
  where to write. No import-path arithmetic.
- **`ctx.fns.<name>(ctx, ...)` calling convention.** No imports between
  project files — so children can be swapped without touching callers.
  The emitter doesn't need to track or rewrite import edges.
- **One file per function.** Each dispatch edits exactly one source
  file + one test file. Reviewing generated code is "read this one
  file" rather than "trace this class through 500 lines."
- **Global types via `declare global`.** `Ctx` is available
  everywhere without imports — bodies stay focused on their logic.

Trade-off: the runtime dispatch via `ctx.fns` is a typed service locator.
Not the most type-safe pattern for hand-written code, but for an agent-
generated codebase it keeps each file independently understandable,
which is exactly what we optimise for.

## Prompt scoping via Prolog

The Implementer prompt for function F shows only a *subgraph* of the
project — computed deterministically by a Prolog query against
`fn/1`, `parent_of/2`, and `calls/2` facts:

```prolog
relevant(T, T).
relevant(T, A) :- ancestor(T, A).            % parent chain
relevant(T, C) :- parent_of(C, T).           % direct children
relevant(T, S) :- parent_of(T, P), parent_of(S, P), S \= T.  % siblings
relevant(T, K) :- calls(T, K).               % direct call dep
relevant(T, K) :- calls(T, M), calls(M, K), M \= T.  % 1-hop transitive
```

`calls/2` is populated by regex-scanning `ctx.fns.<name>` references in
the function's tests and (if present) body. Unrelated corners of the
project don't appear in the prompt — 11k-char context drops to 2-3k.

Fallback: on Prolog error/timeout, return the full function list. A
broken scope query never blocks a build.

## Deterministic resilience features

Built into the harness, not the LLM:

- **Resume on restart** (plan skips declared-phase-1 fns, skips
  phase-2-with-tests fns, skips phase-2b-with-integration, dispatch
  skips tests-green).
- **Project-dir reuse across attempts** (warm vitest module cache;
  rewrite only the changed function's files each attempt).
- **Body extraction tolerant** of fence variants (`js`/`ts`/bare/
  `language:filename` suffix). CRLF → LF normalised.
- **Pre-test before asking the LLM.** An existing body that already
  passes → skip the LLM call.
- **Failure digest over raw vitest output.** Integration failures
  parsed to distill `✗ <name> (integration): <msg>` lines so the
  model sees the assertion, not 4KB of JSON.
- **Stale `tests-green` reopened on finalize failure** — integration
  tests that initially passed but break on a later sibling's body get
  their function re-queued.
- **Graph-mutex** available (`graph.withLock`) for any future async
  critical section — unused today because the build loop is serial.
- **Defensive `ctx` strip** in `addFunctionInternal` — if a planner
  includes `ctx` in params, it's dropped so the emitter's
  injection doesn't produce `function foo(ctx: Ctx, ctx: Ctx, …)`.
- **Name collision prevention**: parent-variant phase-1 prompt lists
  every existing function so the LLM picks distinct names; global
  uniqueness enforced at `addFunction`.

## Why it works

Three principles in tension, resolved:

1. **LLMs are unreliable, but narrowly-scoped outputs are parseable.**
   Every LLM call has a JSON schema or a single-word answer or a single
   fenced block. Never free-form prose, never multi-step reasoning
   that has to be re-parsed. Noise in one call can be retried without
   affecting anything else.

2. **Complex software is decomposable, but decomposition is agentic.**
   The Implementer — not the harness — decides whether to IMPLEMENT or
   DECOMPOSE. This is where domain knowledge lives. The harness doesn't
   try to be smart about decomposition; it just executes the decision.

3. **Correctness comes from tests, not from the LLM's confidence.**
   Unit tests bound each function. Integration tests bound each
   assembly. Project tests bound the application. A function passes
   only when its tests pass against real sibling implementations (for
   integration) or against stubs (for units). Nothing is trusted
   without a test run.

The result is a system where the LLM's job is "describe, write code
that satisfies these tests" — which is the thing LLMs are best at —
and the hard parts (dependency ordering, retry logic, persistence,
tool orchestration) are all in code.
